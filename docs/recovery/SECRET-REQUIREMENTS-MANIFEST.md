# Secret requirements manifest

This is a metadata-only recovery manifest. It records logical names, consumers, authorities, reference paths, and required disposition. It contains no values, ciphertext, hashes, token prefixes, database content, session content, raw environment, or provider authentication output.

## Provisioning policy

1. Prefer the existing `cdenneen/home` SOPS/sops-nix authority for personal and host deployment secrets and Alpha0's narrower SOPS mapping for Alpha0-owned secrets.
2. A destination runtime directory must be mode `0700`. Materialized secret files must be mode `0600` or stricter; canonical mappings that use `0400` remain preferred.
3. Secrets must never enter Git, a Nix derivation or store path, a report, a command transcript, a log, a scheduler record, or an evidence bundle.
4. Encrypted source documents are authority inputs only through sops-nix. A decrypted source file is not a migration artifact.
5. `ROTATE_AND_REISSUE` means issue at the provider/authority, install through the managed mapping, validate least privilege, and revoke the old credential after accepted cutover.
6. `REAUTHORIZE` means create a fresh user/session grant on the destination; caches and temporary credentials are never copied.
7. `REUSE_SECURELY` is permitted only after custody, owner, scope, and continued registration are proved. It never means copy a legacy environment file.
8. `UNKNOWN` blocks activation of that consumer until the producer and lifecycle owner are identified.

The public age-recipient policy in `.sops.yaml` is configuration metadata. Private age identities and decrypted payloads were not inspected.

## Product move subsets

### If `AXIS_CONTROL` changes hosts

Required inputs are the managed GitLab token, PO identity configuration, signed deployment trust/allowed-signer material, and any separately approved Hermes interaction/provider identity. The canonical controller does not require AXIS Core, PostgreSQL, vector, graph, cache, Slack, AWS, or local checkout credentials merely to perform its present GET-only bootstrap/observer role. The missing managed `GITLAB_TOKEN` producer/destination mapping is a blocker.

### If `ALPHA0` changes hosts

Required inputs are the audit key reference, separate Core/gateway secret maps, dedicated Slack bot/app/member identity, API server key, selected provider credential, separate `gitlab.com` and `git.ap.org` observer service credentials where enabled, the independently authorized forced-command node and forwarding-relay identities where needed, and OAuth grants for each enabled integration. The operator `glab_cli_config` is not an Alpha0 service credential. Existing SQLite data is not a secret but must use owner-only encrypted transfer. OAuth caches and AWS sessions are reauthorized, not migrated.

## Explicit legacy exposure disposition

The two legacy AXIS `.env` files recorded at mode `0644` are not secret authorities. The model-provider credential evidenced there is unconditionally **`ROTATE_AND_REISSUE`**. No value, key name, hash, length, prefix, or encrypted payload from those files appears here. Permission repair alone is insufficient; after custody-approved drain, provision a replacement from managed authority and revoke the exposed credential.

## Residual blockers

- Axis-control's GitLab token has a consumer contract but no complete reviewed Home/producer mapping and exact destination.
- Google and Microsoft OAuth require interactive reauthorization.
- Context7 and several Home-declared legacy integrations lack proved consumers/lifecycle owners.
- Exact provider credentials for future AXIS backend placements remain axis-lab admission decisions.
- Existing recipient breadth and private-key custody were not validated.
- Credential existence, scope, expiry, validity, and compromise status were deliberately not tested.
